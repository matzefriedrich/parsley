# GitHub Release Workflow

Use this skill when preparing a release for `matzefriedrich/parsley` with the GitHub CLI (`gh`). A draft is not the same as a published release: never publish a release unless the user explicitly asks for publication.

## Repository conventions

- Stable release names use `parsley vX.Y.Z`, and the tag is `vX.Y.Z`.
- Release notes are editorial summaries, not a replication of the changelog. Focus on features and changes that directly affect developers: explain what changed and why it matters, using a short introduction and relevant `###` sections with concise highlights. Recent releases use `### Key Features`; older notes may use sections such as `### Breaking Changes`, `### Improvements & Fixes`, or `### CLI & Tooling` when appropriate.
- Do not use emojis in release titles or notes.
- Omit routine dependency updates from the release narrative; developers can consult the full generated changelog for those. Mention a dependency update only when it creates a meaningful developer-facing change that warrants highlighting.
- End the notes with a comparison link: `**Full Changelog**: https://github.com/matzefriedrich/parsley/compare/<previous-tag>...<new-tag>`.
- Alpha releases are marked as prereleases. Do not mark a stable version as a prerelease.
- Use `CHANGELOG.md` as the source of truth for included changes and release date/version. Do not invent changes or silently alter the changelog.

## Prepare and verify

1. Determine the intended tag and previous release tag from the changelog and GitHub release list.
2. Check repository identity and authentication with `gh repo view` and `gh auth status`.
3. Check that the intended tag exists and points to the expected commit. If the tag is missing or points somewhere unexpected, stop and ask before creating or moving it.
4. Check `gh release view <tag> --repo matzefriedrich/parsley`. If a release already exists, inspect its state and do not create a duplicate.
5. Review the complete changelog section for that version, identify the developer-facing features and changes, and draft an editorial summary. Do not copy the changelog verbatim or list routine dependency updates; include a full-changelog comparison URL so readers can inspect all entries.
6. For a requested draft, create it explicitly as a draft:

   ```sh
   gh release create <tag> \
     --repo matzefriedrich/parsley \
     --draft \
     --title "parsley <tag>" \
     --notes-file <prepared-notes-file>
   ```

   The notes file must be deliberately prepared from the reviewed changelog section and focus on meaningful developer-facing changes. Do not use an empty notes body or assume autogenerated notes match the repository's narrative style.

7. Verify the result with `gh release view <tag> --repo matzefriedrich/parsley --json name,tagName,isDraft,isPrerelease,publishedAt,body,url`. Confirm the tag, title, notes, and `isDraft: true`; do not publish it.

## Safety

- Creating a draft release is an external GitHub write. Do it only when the user explicitly requests creating/drafting a release; a question about whether it is possible calls for explanation unless the surrounding context clearly authorizes the action.
- Never use `gh release create` without `--draft` in this workflow.
- Never create, move, or push a tag without explicit authorization.
- Do not include unrelated local changes in a release commit or change the changelog as part of drafting unless separately requested.
- If the release's tag, changelog section, authentication, or intended stable/prerelease status is ambiguous, stop and ask a focused question.
